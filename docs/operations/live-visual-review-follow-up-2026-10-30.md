# План визуальных доработок по опубликованным сайтам

Дата проверки: 30 октября 2026 года.  
Среда: BrowserOS neo, опубликованные GitHub Pages draft, viewport около 953×954 CSS px.  
Проверенные URL:

- <https://wellnessnd.github.io/ru/>
- <https://wellnessnd.github.io/ru/booking/>
- <https://nd-science.github.io/ru/>
- <https://nd-science.github.io/ru/publications/>
- случайные отсутствующие URL обоих сайтов.

Этот документ описывает задачи по опубликованному состоянию. Перед реализацией сравнить их с текущим `HEAD`: опубликованный Wellness отстаёт от локальной версии.

## 1. Общая задача синхронизации

Ответственные: DevOps и QA.

1. Сопоставить production commit каждого GitHub Pages deploy с текущим репозиторием.
2. Добавить видимый release SHA или build metadata в диагностический artifact, не в пользовательский интерфейс.
3. Не оценивать исправленную локальную задачу как опубликованную до проверки реального URL.
4. После каждого deploy проводить короткий smoke: header, footer, RU/EN, CTA, 404, sitemap, robots.

Критерий: для каждого опубликованного сайта известны commit, время deploy и результат smoke.

## 2. Wellness — визуальные задачи

### W-VIS-01. Убрать признаки устаревшего deploy

На опубликованной версии всё ещё видны:

- верхняя плашка «Черновик: сайт ещё не выпущен…»;
- footer `Wellness · Черновик (noindex)`;
- «Самозанятая Долгова Н. А.» вместо утверждённых инициалов;
- отсутствующая вкладка контактов в видимой опубликованной навигации.

Исполнитель обязан не исправлять это повторно вслепую, а сначала проверить, присутствуют ли исправления в текущем `HEAD`, затем выпустить согласованный commit и подтвердить реальный URL.

### W-VIS-02. Сократить визуальную дистанцию до CTA

Первый экран читается как длинная статья: крупный H1, metadata, несколько длинных абзацев, квалификации и список запросов. Основное действие теряется ниже текста.

Задача:

- оставить в hero короткое позиционирование;
- показать цену и основной CTA раньше;
- переместить методическое объяснение ниже;
- разбить квалификации и запросы на компактные proof-блоки;
- сохранить спокойную профессиональную подачу без агрессивной продажи.

Критерий: основной CTA находится в первом визуальном сценарии desktop и 390 px.

### W-VIS-03. Навигация вкладками

При ширине около 953 px ряд уже горизонтально прокручивается и занимает значительную часть верхней зоны.

Задача:

- сохранить метафору вкладок;
- сделать очевидным наличие скрытых пунктов справа;
- удерживать активную вкладку в видимой области;
- уменьшить визуальный шум scrollbar;
- проверить, можно ли вынести вторичные направления на второй уровень без потери концепции;
- не прятать главный путь «Запись и контакты».

### W-VIS-04. Footer

Footer перегружен навигацией, профилями, внешними legal-документами и реквизитами.

Задача:

- разделить primary navigation, contact, trust и legal;
- добавить HTML sitemap;
- first-party legal pages поставить перед внешними приложениями;
- исправить heading hierarchy;
- убрать повторение формулировок draft после production GO.

### W-VIS-05. Booking

На опубликованной странице форма отсутствует; видны блоки «Форма первичного обращения» и «Форма подключается отдельно».

Задача:

- до подключения оставить однозначное draft-состояние только в закрытом preview;
- в production показывать форму либо честный рабочий контактный сценарий;
- разместить price/format summary и четыре шага выше длинных условий;
- не создавать ложного ощущения завершённой записи.

## 3. Science — визуальные задачи

### S-VIS-01. Сохранить сильные элементы

Сохранить:

- академическую синюю тему;
- ясный H1;
- два видимых CTA;
- выраженное отличие от Wellness;
- обновлённую навигацию и отсутствие draft-плашки.

### S-VIS-02. Сбалансировать hero

Hero визуально сильный, но крупный голубой градиент занимает большую часть первого экрана, а доказательные блоки начинаются ниже.

Задача:

- уменьшить вертикальный объём hero на внутренних страницах;
- на главной добавить компактную строку доказательств или направлений без перегрузки;
- не превращать декоративные blobs в ложную инфографику;
- сохранить читаемость крупного serif H1.

### S-VIS-03. Навигация

При ширине около 953 px крайние пункты требуют горизонтального scroll.

Задача:

- сохранить папочные вкладки;
- показать scroll affordance;
- гарантировать доступность «Контакты»;
- проверить длинные EN labels;
- не уменьшать шрифт ниже комфортного уровня ради размещения всех пунктов.

### S-VIS-04. Publications

В RU-фильтре опубликованы технические английские значения: `conference paper`, `thesis`, `journal article`, `book chapter`.

Задача:

- локализовать labels;
- оставить стабильные внутренние enum отдельно от отображаемого текста;
- показать фильтр и первые публикации выше длинного вступления;
- унифицировать DOI, источник, год и copy-citation;
- проверить keyboard и screen-reader управление select/filter.

### S-VIS-05. Footer и sitemap

Ссылка «Карта сайта (Sitemap)» ведёт непосредственно на `sitemap.xml`.

Задача:

- создать HTML sitemap RU/EN;
- назвать XML-ссылку технически либо не показывать её пользователю;
- добавить отдельную ссылку на HTML sitemap;
- исправить footer heading outline H1→H4;
- сохранить научные профили, но визуально отделить их от legal.

## 4. Оба сайта — 404

Случайные отсутствующие URL обоих сайтов показывают стандартную англоязычную страницу GitHub Pages:

- отсутствует бренд;
- нет RU/EN;
- нет ссылки на главную сайта;
- нет основных пользовательских путей;
- пользователь попадает в документацию GitHub Pages.

Исполнитель обязан реализовать custom 404 по [плану технических страниц](technical-pages-and-system-states-plan-2026-10-30.md) и проверить реальный status.

## 5. Визуальная перепроверка

После реализации повторить BrowserOS-проверку:

1. Wellness home RU/EN.
2. Wellness booking RU/EN.
3. Science home RU/EN.
4. Science publications RU/EN.
5. HTML sitemap обоих сайтов.
6. Custom 404 RU/EN обоих сайтов.
7. Footer и navigation на 320, 390, 768, 953 и 1440 px.
8. Zoom 200% и 400%.
9. Keyboard focus и `prefers-reduced-motion`.

Сохранить screenshots с commit, URL, viewport и датой. Не использовать screenshot как единственное evidence для HTTP status, schema, accessibility и формы.
